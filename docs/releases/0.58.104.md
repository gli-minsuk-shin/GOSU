## Why the scheduled briefing took 15 minutes

User report: the scheduled briefing is far slower than an earlier OpenClaw morning briefing that
"read mail with AppleScript".

OpenClaw evidence (read-only, `~/.openclaw_bak`): the fast job `매일 아침 브리핑 (디스코드)` took
50.6s and used no AppleScript. It called the `gog` Google Workspace CLI (Gmail API search
`is:unread in:inbox --max 5` per account, subject/sender only, no bodies) and made one Gemini 3 Flash
turn. Its sister job `매일 아침 브리핑 (iMessage)` failed after 932.6s with an LLM timeout.

GOSU evidence (`native-usage-ledger.v1.json`, 2026-09-17): one run made 14 sequential
`briefing_summary` calls from 21:06:24 to 21:20:43, the next 13 calls from 21:25:20 to 21:40:13;
each Haiku batch of six items took 17–218s (median about 55s). Mail reading takes about 1.5–3
minutes; the AI batches are the bulk of the run.

Measured with the real Claude Code CLI 2.1.272 on synthetic metadata for 30 emails (no real mail):
Haiku with `--effort medium` took 43.6s (4,456 thinking tokens), `--effort low` 65.2s (6,833
thinking tokens), and with `MAX_THINKING_TOKENS=0` and no `--effort` 4.8s (0 thinking tokens) with an
equivalent result. Extended thinking is about 90% of that call's latency.

## Changes (user choice: quick first briefing, concurrent batches)

- **Concurrent summary batches.** `runBatchesConcurrently` runs email batches three at a time and
  paper batches two at a time (paper batches also read arXiv HTML and figures). Emails still finish
  before papers start. A per-batch failure stays a warning; a fatal error (cancel, settings, consent,
  login, subscription, model) stops new batches, aborts the in-flight ones and is rethrown after they
  settle. Concurrent batches share one model resolution. The stores already serialize writes.
- **Quick first briefing.** Right after sources are collected, one metadata-only call (email subject,
  sender, account, received time, read state, a preview of at most 200 characters when the body was
  read, paper titles, the agenda) writes a headline and up to six points. It runs beside the detailed
  batches, is saved as `snapshot.quickBriefing` on the day's entry (marked private) and shown at the
  top of "먼저 확인할 내용" with its basis stated. `quickBriefingAt` on the job makes the history
  view reload at once (the refresh stamp previously changed only with the summary count). It uses the
  `lightweightTasks` model route and runs only where the detailed email summaries would run without
  asking (mail AI allowed, private AI allowed for that provider, no per-request confirmation). Its
  failure adds a warning and never fails the run.
- **Thinking disabled for the quick call only.** `structuredJob.thinking: 'disabled'` reaches
  `runTurn`; the Claude Code adapter then omits `--effort` and sets `MAX_THINKING_TOKENS=0` for that
  process. Other providers ignore it. Detailed summaries keep the user's reasoning setting.

- **"사고 끔" reasoning level for Claude Code (user request, default).** The Claude Code catalog now
  lists `off` ("사고 끔") first and marks it as the default; a turn with `off`, or with no explicit
  level ("모델 기본값"), runs without `--effort` and with `MAX_THINKING_TOKENS=0`. The Claude Code
  default collaboration mode recommends `off`; plan mode still recommends `high`. Every settings
  screen that lists catalog reasoning options (Settings → AI agent → 모델 설정, default AI, project
  chat, Briefing) offers it. The real CLI accepted a zero thinking budget with `--json-schema` on
  Haiku (4.8s above), Sonnet 5 (2.0s) and Opus 5 (3.8s), each reporting 0 thinking tokens.

Not changed (user choice "설정에서 정할 수 있게 해줘"): saved settings. Profiles that name a level
keep it — here `fast` Haiku `medium` (Briefing, light tasks), `lightweight` Haiku `low`, `strong`
Opus 5 `xhigh`; the user selects "사고 끔" in Settings. Also unchanged: the manual automatic-summary
job and mail reading.
