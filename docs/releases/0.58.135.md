## Packages carried every earlier Model Lab and Briefing Lab bundle

Reported from the 0.58.133 package and measured on the installed 0.58.134 package
(`apps/desktop/dist/mac-arm64/GOSU.app`, ASAR SHA-256 `23bc15ee…6abac1`): `out/model-lab` held 141
files with 80 `.js`/`.css` bundles and `out/briefing-lab` 206 files with 143, while each `index.html`
loads exactly one script and one stylesheet. The other 219 bundles (the oldest from 2026-09-07) were
never loaded, but they were 235 MB of a 313 MB ASAR, and a bundle inspection that greps every asset
found code that no longer exists in the source (for example the class `module-detail-copilot__saved`).

- **Root cause**: the `bundle-model-lab` plugin in `electron.vite.config.ts` copied
  `apps/model-lab/dist` and `apps/briefing-lab/dist` into `apps/desktop/out/<lab>` with `mkdir` +
  `cp(recursive)`, which merges into whatever is already there. Vite empties each lab's own `dist`
  (one script and one stylesheet there) and electron-vite empties only its own `out/main`,
  `out/preload` and `out/renderer`, so nothing ever emptied `out/model-lab` or `out/briefing-lab`.
  Every build has new content-hashed names, so every build added a pair, and electron-builder's
  `out/model-lab/**/*` and `out/briefing-lab/**/*` patterns packaged all of them. This was noted as
  an observation in 0.58.111 and not fixed then.
- **Fix** (`replaceLabBundle` in `scripts/lab-bundles.mjs`, used by the plugin for both labs): check
  that the lab's `dist/index.html` exists, remove the desktop copy, then copy. A lab that was not built
  stops the build with `Lab bundle is not built: <path>/index.html is missing` and leaves the existing
  desktop copy alone. `out/main/python-architecture-analyzer.py` is copied as before.
- **Package check** (`verifyPackagedLabBundles`, run by `verify-packaged-app-startup.mjs` before the
  startup smoke, so every `package:mac:*` script gates on it): reads the ASAR header directly
  (`@electron/asar` cannot be resolved from `scripts/` under pnpm), starts at each lab's `index.html`
  and follows file names through the bundles it reaches (lazy chunks, their styles, workers). Any
  `.js`, `.mjs` or `.css` under `out/model-lab/assets` or `out/briefing-lab/assets` that nothing
  reaches fails the verification with the count and the first 12 paths; a lab whose `index.html` is
  not packaged fails too. Fonts and other assets are not judged: their hashed names only change with
  their content, and they are replaced with the rest of the copy.
- **Turbo**: `turbo.json` lists `scripts/lab-bundles.mjs` and its `lab-bundles.d.mts` under
  `globalDependencies`, following the repository's rule for files imported across packages. Turbo
  hashes a package's own files only, so without this a later change to the copy step would replay a
  cached desktop build. `turbo-cache-policy.test.mjs` now fails for any `../../` import in
  `electron.vite.config.ts` that is not a global dependency; `turbo run build --dry=json` lists both
  files under `globalCacheInputs`. Adding them changes the global hash, so the first check after this
  runs every task uncached.
- **Not changed**: the Turbo task still caches `out/**`, and a cache restore writes over `out/`
  without deleting. Packaging never goes through Turbo (`package:mac:*` runs the desktop `build`
  script itself), so a package always gets a replaced copy, and the package check fails if it does not.

## Briefing runs on the models from Settings → Agent

User request (2026-09-21, after 0.58.133 had made a Briefing run fall back to the routine's own model
with a notice): "AI agent 세팅에서 이메일 요약이랑 AI 비서랑 무슨 LLM model 쓸 지 정하잖아? Briefing 에서
다른 모델 쓰는게 말이되나? Briefing 설정에서 AI model 선택하는거 없애고 Agent AI 설정에서 정하는 모델로
Briefing 돌아가게 만들어줘." Two places decided Briefing's model: Settings → Agent (role models per
usage) and Briefing's own engine/model/reasoning picker (in its settings and in the chat header). When
they named different providers the routine's provider won, so the model the user had chosen in
Settings → Agent was silently not used (0.58.130 failed the run, 0.58.133 ran the other model and
said so).

- **One rule** (`routedBriefingPreferences`): for every Briefing usage (`briefing` = email and paper
  summaries, re-summaries and paper field classification; `briefingAssistant` = the AI assistant
  chat, global or in Briefing; `lightweightTasks` = the quick first briefing and event/to-do drafts)
  the provider, model and reasoning come from the role assigned in Settings → Agent. A model stored
  with the routine wins nowhere any more, not even in the assistant chat. Only while that role has no
  model there ("미지정" or "기존 설정") does the routine's stored selection run; nothing in the UI changes
  that stored selection now, and it is not rewritten, so the approved scope and the saved conversation
  of each routine continue without a new approval.
- **Private data follows the same decision** (`BriefingWorkspaceStore.providerAllowed`): `canPrivateAi`
  and `assertMail` used to accept only the provider stored with the routine. They now also accept a
  provider that Settings → Agent assigns to one of the three Briefing usages
  (`briefingRoutedProviders`). `model-routing.v1.json` is written only by the desktop Settings screen
  through a sender-checked IPC handler; the Briefing page cannot change it. A provider that is neither
  stored nor assigned is still refused, as is everything when the routine does not allow AI
  (`mailAi`), is not approved or is not owned by this client. The approval dialog on saving Briefing
  settings says "AI 모델: 설정 → Agent의 작업별 AI 모델을 따름 (현재 Codex)" instead of naming one
  provider. The assistant checks permission for, and runs on, the provider it was routed to; the
  error `model_routing_provider_permission_required` no longer exists.
- **Removed**: the engine/model/reasoning selects in Briefing settings, the model popover in the chat
  header with its endpoint `/assistant/model/save` and `briefing-model-settings.ts`, the chat's
  "blocked while the model is being saved" state, the 0.58.133 notice (`roleRoutingNotice`), and the
  error texts that only that picker produced. The removed source files were moved out of the
  repository to the session scratchpad, not deleted.
- **Shown instead** (`BriefingAgentModels`, `BriefingModelBadge`, endpoint `/assistant/model/current`
  now reporting all three usages): Briefing settings list which provider, model and reasoning each
  usage runs on right now, say so when Settings → Agent assigns none (the routine's earlier model
  runs) or when the model cannot be used with the current connection, and have a button
  "설정 → Agent 열기". The chat header shows the assistant's model read-only; a click opens the same
  screen (message `gosu-open-agent-settings`, accepted only from the owned Briefing frame and origin).
  The list refreshes when the window regains focus and when a chat turn ends.
- **Settings → Agent** says that Briefing runs on these models, has no picker of its own, and that
  what Briefing allows for AI goes to the provider of the model assigned here. For the three Briefing
  usages the "기존 설정" choice reads "기존 설정 · 루틴이 전에 쓰던 모델".
- **Not changed**: the Routine Copilot (drafting a routine from a description) still has its own
  model list; it sends no mail or calendar data and has no usage row in Settings → Agent. Project
  Chat's per-chat model choice is unchanged. `paper-summary-ingestion` no longer fails with "Briefing
  Lab에서 논문 요약 모델을 설정해주세요" when a routine has no stored AI preferences; it uses the defaults
  under the same rule.
- **What the user should know**: with the current settings (all three roles on Codex) mail summaries,
  the assistant and drafts now go to Codex, where this routine used Claude before. The consent
  "허용한 메일·일정…을 LLM에 전달" in Briefing settings stays the switch for whether private data goes to
  any model at all.

Regression tests: `briefing-generation.test.ts` (the assigned model runs whatever provider the
