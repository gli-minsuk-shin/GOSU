## A question inside the module detail looked like it did nothing

User report: asking about the AI explanation inside the module detail gets no reaction at all.

Evidence from the saved Model Lab conversation: both questions reached Model Copilot (the follow-up
prompt is in the chat at 08:43 and 08:45 KST on 2026-09-21) and both failed about 0.4 seconds later
with the generic "GOSU Model Copilot is unavailable" message. The dialog did report it, but the alert
was rendered at the top of the AI section, above a long saved answer, while the reader was at the
question box at the bottom. The box got its text back in the same frame, so nothing visible changed.
The same generic failure also happened once on 2026-09-20 before two explanations succeeded, so it
is intermittent; the saved message does not keep the server's failure code, so the underlying cause
of those three failures cannot be read back.

- The failure is now shown beside the question box, under the discussion, where the reader is, and
  the failed turn itself is part of the visible conversation.
- The adapter used to collapse every unmapped server code to `model_copilot_llm_unavailable`. It now
  keeps a plain code (`modelLabRuntimeErrorDetail`; sentences, logs and secrets are still dropped),
  gives actionable messages for the fast failures the server can raise before any model call
  (selected model or reasoning level no longer in the catalog, selected module or active model
  missing, request too large, empty answer, agent could not start, step limit, catalog unavailable),
  and appends "Error code: …" to the generic message for any other code. The next failure names its
  cause instead of "unavailable".

## The discussion is a panel on the right

User request: not at the very bottom; open a session on the right so answers are easy to read and
questions easy to ask.

- The module detail is two columns when Model Copilot is available: the detail scrolls on the left,
  the discussion scrolls on the right with the explain button on top and the question box pinned at
  the bottom (dialog up to 1420px wide and 900px tall). From 1280px down the detail becomes one
  column and the panel narrows; only under 860px does the panel move below the detail.
- A new answer scrolls into view at its first line, a running turn keeps its status in view,
  another module starts at the top of its own discussion, and the cursor returns to the box when the
  answer arrives. Enter sends (not while composing Korean), Shift+Enter breaks the line.

## Module questions continue the one Model Copilot conversation

User follow-up while this was being built: are the discussions separate per module? Then talking in
one module about the previous one does not connect; it should continue in Model Copilot, where each
question says which module it came from and roughly what that module is.

They were already sent through the same Copilot conversation, but the panel showed a per-module
thread and the Copilot panel showed the whole 2,500-character prompt as the user's message.

- The right panel is now the Model Copilot conversation itself. Moving to another module keeps
  everything said so far; exchanges about the open module are marked, and opening a module scrolls
  to its latest exchange (or to the end when it has none).
- A module turn is an ordinary Copilot message with a `moduleRef` tag: module id and key, name,
  location ("FOR-LOOP · step 2") and one line on what the module does. The message body is just
  the question ("이 모듈을 자세히 설명해줘." for the explain button). The model still receives the full
  prompt with the module's source, equation, data flow and block notes (`prompt`).
- In the history sent with every later turn, a tagged question is prefixed with its module
  (`moduleConversationBody`), so "the module we discussed before" is meaningful from anywhere.
- Both panels render the tag (`ModuleQuestionTag`); it opens that module's detail, also for a step
  inside a loop (`findGraphModule`). Raw prompts saved by 0.58.125–0.58.127 are read back as the
  question and module they carried (`legacyModuleQuestion`), so the existing conversation is tidy too.
- The per-module store stays as the durable record: it drives the card mark, and if the conversation
  no longer holds a module's discussion the saved one is offered in a collapsed block.

## Every module explains itself without AI

User request: even without the AI explanation there should be enough explanation to get the basic
idea; today there is almost none.

"이 모듈의 역할" showed only the pseudocode `notes:` text, or the raw source when there were none. It
now always has a deterministic reading (`moduleReading`): what kind of module it is and what that
kind does, its group, repeat count and parent block, input and output shapes and named ports with
their binding; the computation order statement by statement (for/if nesting kept, author comments
attached, at most 12 lines with the rest counted); then activation, parameter count, what it receives
from and sends to which module, shape notes, unresolved points and the code reference. The author's
notes stay on top as written. A loop step keeps its existing generated description and gains its
shapes and wiring. The text is Korean or English with the app language, restates only what the
pseudocode and graph say, and says so.

## Cards show which modules were explained

Graph cards carry an "AI 설명" mark when a Model Copilot discussion of that module is saved. A
collapsed loop card is marked when any step inside its iteration was discussed, so it is visible
from the whole-model view.

## Briefing AI assistant: jump to the latest message

User request: a button in the AI assistant chat that goes straight to the newest conversation, in
the Project Chat design. The Briefing chat now shows the same round "↓ 최신" control at the lower
right of the conversation while the newest message is more than 96px out of view (Project Chat's
rule); one click scrolls to the end. In the full-page assistant it stays on the centered column.
