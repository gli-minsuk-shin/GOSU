## What was asked about a paper is kept with that paper

User request: "논문 요약에 AI 랑 이야기한 내용을 요약 저장해서 해당 논문에 저장해서 나중에 check
하게 하자."

- A question asked about a paper that is in the 논문 요약 보관함 is recorded on that paper: the
  question in the user's own words, the opening of the answer the model already wrote, and when it
  was asked. The newest 40 turns are kept and the total keeps counting, so a row can say how much
  was discussed without the record growing without a bound.
- **No second model call.** The record is derived from the turn that already happened. A summary
  written by a model would mean one more call per question, and the user's own question is a truer
  index of what was discussed than a paraphrase of it. If a model-written paragraph is wanted later,
  it is an addition to this record, not a replacement.
- Which paper a chat is about comes from the reference the chat already carries. A card in the
  보관함 builds its chat button with an empty `historyId` and the record's own 64-hex id, and
  `sharedPaperView` publishes the same id, so `savedLibraryPaperId` accepts either form and refuses
  everything else. A paper from a briefing's own history is not in the 보관함 and is not recorded.
- The record is written into the sealed library file by a read-modify-rewrite: `noteConversation`
  reads the record, appends the turn and renames the new sealed file over the old one. Creating a
  record still uses create-only linking, so two processes cannot overwrite each other's analysis;
  only a record's own note replaces it. The analysis, its id and its `savedAt` are untouched.
- A note that cannot be written never costs the answer. The answer is delivered and the chat's
  status line says what happened, with a separate sentence for a paper that is not in the 보관함.

## 논문 요약 marks and filters the papers with an AI conversation

User request: "나중에 대화 나눈 논문을 쉽게 찾을 수 있게 AI 대화 아이콘을 붙여서 다른 논문과
구분하게 하자. 그리고 논문 요약 ssession 제일 위에서 AI 대화 질의응답한 논문 들만 filtering 할 수
있게 하자. 여러 검색 옵션과 같이 조합해서 검색할 수 있게도 하자."

- A row for a paper with a conversation carries the chat mark and the number of turns, with the last
  question in its tooltip.
- "AI 질의응답 (n)" sits in the filter row at the top of 논문 요약, next to the search box, the
  category and the tags. It is a switch, not a mode: it intersects the text search, the category,
  the tags and both date ranges instead of replacing them. Turning it off restores the whole list.
- Filtering reads the saved records only. No source is opened and no model is called, which is what
  the line under the filters already promised.

## 추가 or 나중에 when no link can be verified

User request: "여기서 추가, 나중에 버튼으로 선책할 수 있게 하자."

- The state where an answer holds no link the library can open used to be a sentence with nothing to
  press, in both AI 비서 and Project Chat. It now offers two buttons.
- The first is **링크 붙여 다시 정리**, not 추가, and that is deliberate: in this state there is
  nothing the library can add, so a button labelled 추가 would promise a save that cannot happen.
  One click sends "논문마다 DOI나 arXiv 링크를 붙여서 다시 정리해줘" as the user, which is the
  sentence the notice used to ask them to type. 나중에 puts the buttons away and keeps the
  explanation.
- Both chats send it the same way. Project Chat's `submit` now takes the text to send, so a card can
  send a follow-up in the user's place; its send button had to stop passing its click event as that
  text.

## One naming decision to overrule in a word

The user asked for "추가, 나중에" buttons in the state where an answer holds no verifiable link. The
second is 나중에. The first is **링크 붙여 다시 정리**, because in that state the library has nothing
it can add and a button labelled 추가 would promise a save that cannot happen; the click asks for
the links that would make a save possible. If 추가 is wanted anyway, it is one string in
[the offer card](../../apps/briefing-lab/src/paper-summary-offer.tsx).
