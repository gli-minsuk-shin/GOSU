## A paper nobody opened is no longer built

The user asked why 논문 요약 scrolls badly, then answered it themselves: "expand 안한 내용은 굳이
읽을 필요가 없잖아?" They were right, and the measurement is worse than it sounds.

One paper card renders **296 HTML tags**, and **242 of them are the collapsed body** — 82%. Behind
those tags sit a Markdown parse and KaTeX typesetting, and KaTeX builds an HTML tree _and_ a MathML
tree for every formula. The list is not virtualised and grows thirty cards at a time:

| cards | before      | after     |
| ----- | ----------- | --------- |
| 30    | 8,880 tags  | **1,620** |
| 101   | 29,896 tags | **5,454** |

The body is now built the first time a paper is opened, and kept afterwards so opening and closing
the same paper again is instant. It applies to the 논문 요약 library and, at the user's prompting,
to the briefing feed as well.

**The saving is per paper body, not per page.** Measured on the briefing-feed test fixture — mostly
weather, agenda and mail chrome around two short papers — the whole feed shrank about a tenth. A
library of thirty papers is where the 82% is felt. The test says so rather than implying the bigger
number everywhere.

### Why it is opt-in rather than the default

Turning it on for every paper card broke 15 tests that assert what an _opened_ paper shows. Those
are real guarantees, so the flag is off by default and the two list containers set it: a briefing
shows a handful of papers, a library shows thirty and counting. That took the breakage to one test,
which now opens the card the way a reader does and additionally pins that a collapsed card has no
body. Three tests that assert summary text through a static render — which cannot open anything —
render the feed expanded instead, and not one assertion was deleted.

## Coming back to a chat no longer lands in the middle

Reported for every GOSU AI chat: leave a session, come back, and the transcript shows some spot in
the middle instead of where you were.

The restoring machinery was not the problem — `scroll-settle.ts` exists for exactly this and holds
a position while the layout settles. What was wrong is what it was given. The placement effect did:

```js
node.scrollTo({ top: … ? node.scrollHeight : position.top });
position.top = node.scrollTop;   // ← the reader's saved position, overwritten
```

A pane that has just come back is often still growing — maths, fonts, code blocks — so asking for a
saved offset of 800 is clamped to whatever can be scrolled at that instant, say 100. That clamped
number was then written back over the reader's own. The real position was gone, and every later
placement used the wrong one. The regression test fails on the old code with exactly
`expected 100 to be 800`.

Only the reader's own scrolling updates the position now. The scroll event the placement itself
causes is recognised by where it landed rather than by a timer — the first attempt used a frame
callback, which never fired in one of the hosts this runs in and swallowed the reader's scrolls
instead; two existing tests caught that immediately.

## 논문 요약 can be sorted

Four orders: **요약일 최신순** (the default), 공개일 최신순, 제목 ABC순, 중요도순. The previous
behaviour was importance-first, which is now one choice among four rather than the only one.

Three decisions worth stating. A paper with no date sorts **last**, not first: an unknown date is
not "the oldest", and putting it at the top pushes down what the reader is looking for. Titles use
English-leading collation because the request was "ABCD 순" and most paper titles are English;
Korean collation would put Hangul first. Numbers compare numerically, so "Study 2" precedes
"Study 10", and case is not a rank.
