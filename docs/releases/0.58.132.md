## To-do list and Board: one line per task, a title-first card, a slim toolbar

User request: "To-do list 랑 보드 디자인을 좀더 sharp 하게 바꾸자. 지금은 낭비되는 공간도 너무 많고 좀
산만함. 좀 더 effective 하고 efficient 한 형태로 바꾸자." A mockup of the direction below was shown first and
approved ("진행").

What was wrong, from the real components rendered with twelve example tasks: three header lines plus a
filter card with labels above every field, an add-task card with its own labels and help text, and a
second "TO-DO VIEW / Tasks by workflow stage" heading came before the first task; a to-do row was three
lines with an Edit and a red Delete button on every row; a Kanban card put the priority tag beside the
title, so titles wrapped into three or four lines, and ended with "v1 · Sep 21", ← Edit → and a red
Delete; every column repeated "Across active projects" or "Rename"; a column reserved 350px even for one
card; status badges repeated the column or group the task already sat in.

Behavior is unchanged: drag and drop between columns, the move/edit/delete/complete actions and their
accessible names, filters, Task trash, board settings (names, order, WIP limits), search-result focus,
opening a project's board from the all-project view, and the optimistic-version updates.

- **Toolbar** (`.task-toolbar`): the title with its count, the Kanban/To-do switch, Task trash and
  settings on one line; the filters sit beside it when the pane is wide enough and wrap below otherwise
  (the header then stretches so its actions stay at the right edge). The eyebrow lines ("WORKSPACE TASKS",
  "PROJECT BOARD") are gone.
- **Filters and quick add are one row of controls each.** The field labels stay in the markup for
  assistive technology (`.field-label`, visually hidden only inside these two bars); the controls name
  themselves ("All priorities", "Any date", a placeholder). The all-project quick add now starts with the
  title field. The help sentences became tooltips (the project select, the board's title field). "More
  details" still opens description, priority, due date and labels with visible labels.
- **To-do row** (`.todo-task-row`, 34px): checkbox, priority in a fixed column so titles line up, the
  title taking the free width, labels, the owning project (all-project view) and the due date against
  the right edge. The description is the title's tooltip and is edited as before. The second heading
  above the groups is gone; a group header is 26px.
- **Kanban card**: the title over the whole card width (two lines at most), then one line with
  priority, due date, labels and the owning project; the project board keeps one line of description.
  No version/date footer. A column is as tall as its cards (160px minimum).
- **Actions on demand**: edit and delete (rows) and move left/right, edit, delete (cards) are icon
  buttons (`TaskIcon`) that appear with the pointer or with keyboard focus (`:hover`, `:focus-within`);
  on a card they sit in a corner strip over the end of the title. They stay in the markup, focusable,
  with the same `aria-label`s. The per-column "Rename" is a pencil that appears on the column header the
  same way.
- **Due dates** (`TaskDue`, `compactTaskDue`): "Today", "Tomorrow", "Tomorrow 9:00 PM", "3d late", or a
  short date ("9/25", with the year only when it differs); Korean "오늘 / 내일 / 3일 지남". Only today
  and overdue are red. The full date stays in `title` and `dateTime`. Day differences are whole calendar
  days (UTC ordinals), so month and year boundaries and DST are safe.
- **Less color**: the project chip is neutral; color is left to priority and an imminent due date. A
  status badge is no longer repeated on every task. One case keeps it: in the all-project view, a
  project's own stage name ("PI Review", "Running") is shown as quiet text when it differs from the
  shared column name (`WorkspaceOwnStage`), because that is information the column does not give.
- **Narrow panes**: compact controls keep the one-row bars down to a 760px pane (all-project view; was
  1080px) and 650px (project board; the 900px two-column filter layout is gone). Verified at 820px:
  no horizontal page overflow, rows stay 34px, the board scrolls sideways as before.
- Seven message keys that no longer have a caller were removed from `desktop-messages.ts`; "Tomorrow",
  "{days}d late" and "Stage in this project" were added.

Measured on the real components with the app's type scale (twelve tasks, 1280px window, 1180px pane):
the first to-do row starts 159px from the top and all twelve tasks end at 703px; rows are 34px; the
board starts at 132px and cards are 59-98px (all twelve tasks on one screen). The "before" figures
quoted with the proposal (first row at 452px, rows 83-112px, board at 334px, cards 213-285px) came from
a preview that did not load `@gosu/ui/typography.css`, so its text was larger than the app's and those
figures overstate the old layout; measured the same flawed way, the new layout gave 171px / 34px /
142px / 71-150px.

Regression tests: `task-compact.test.tsx` (new, 4: day names and calendar-day arithmetic, short label
with full-date tooltip in both languages, timed tasks, no due date), `workspace-tasks-view.test.tsx`
(+1: one header, no repeated stage, own stage kept, compact due, icon actions with names, in both
layouts), `board-layout-css.test.ts` (+2: 34px one-line row, actions hidden at rest and revealed by
hover and focus-within, column minimum, title clamp; labels hidden only visually; the narrower break),
`board-settings-view.test.tsx` and `desktop-domain-language.test.tsx` (updated for the removed heading,
eyebrow and button text).

## Found on the way: two process tests assumed a new script starts within 500 ms

`git-blob-batch-reader.test.ts` (timeout kills the process group) and `manuscript-pdf-compiler.test.ts`
(dispose kills every command group) write a shell script and gave it 500 ms to start. macOS scans every
newly written executable first; on this Mac today a brand-new script took 0.26-0.54 s to start while
`XprotectService` was busy, and the first test failed on its own, repeatedly. The reader's timeout is now
2 s and the ready-file wait 1.5 s; what the tests assert is unchanged.
