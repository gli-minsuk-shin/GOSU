## GPT-6-Astra kept disappearing from the model list

User report: "GPT 6 Astra 는 왜 또 사라짐?"

GOSU keeps no model list of its own; it shows what the Codex app server returns for `model/list`.
Evidence: GOSU's isolated Codex home had a `models_cache.json` fetched by client 0.149.0 with six
models and no `gpt-6-astra`, while the user's own `~/.codex` cache, fetched two minutes apart by
client 0.154.0 for the same imported login, had seven including `gpt-6-astra`. The service lists
models by client version. GOSU was running its bundled Codex 0.149.0 because discovery accepted only
stable version strings: the ChatGPT app's runtime had been `0.154.0-alpha.6.2` since its update on
2026-09-15, and the Homebrew runtime (0.153.4) lives in `/opt/homebrew/bin`, which an app opened from
Finder does not have on PATH (and it is a `#!/usr/bin/env node` script whose node sits beside it).
Every alpha build of the ChatGPT app therefore dropped GOSU back to 0.149.0 and its shorter list.

Checked before changing anything: started with GOSU's exact app-server arguments (`--strict-config`,
every disabled feature, config overrides) and a throwaway Codex home, both the ChatGPT app's alpha
runtime and the Homebrew runtime initialize and list `gpt-6-astra`.

- Discovery now orders versions semantically and accepts prerelease builds: a prerelease ranks below
  its own release and above older releases, identifiers compare numerically, and the guard that keeps
  the bundled runtime across a different major version stays. The user agreed to accept alpha builds.
- `/opt/homebrew/bin/codex` and `/usr/local/bin/codex` are candidates on macOS. Such a runtime is
  probed and started with its own directory first on PATH (`codexRuntimeEnvironment`), in the desktop
  app server and in the Model Lab Codex calls.
- If the chosen installed runtime cannot start or initialize, the app server logs a diagnostic and
  starts the bundled runtime instead, so a broken prerelease cannot take Codex down. An explicitly
  configured `GOSU_CODEX_BIN` is never replaced.

## The Obsidian vault looked unconfigured again

User report: "Obsidian 을 연구노트에 붙이는 설정은 또 왜 사라짐?"

The setting was not lost: the vault root is a `cache_records` row in the encrypted local database,
which installs do not touch, and all six project folder markers in the vault still carry the current
vault id. What the code did: the saved vault was reconnected once, at the end of startup, after the
Codex start and several reconciliations, with `vault.restore().catch(() => null)`. Until then, or
forever after one failed attempt, `researchNotes.current` returned `null`, which the screen shows as
the first-time "Connect an Obsidian Vault". Startup is slowest right after an install, and five
versions were installed in two days. Which of the two (the delay or a failed attempt) the user hit is
not known: the app keeps no log, and GOSU's own reader opens this vault in about 0.3 seconds with
1,256 documents from a terminal.

- `VaultAccess.restore` is single-flight, repeatable, never replaces a vault chosen meanwhile, and
  records why it failed (`missing`, `permission_denied`, `unreadable`).
- `ResearchNotesService.current` reconnects the saved vault when none is connected. A saved vault that
  cannot be reopened is reported (`research_notes_vault_missing`, `…_permission_denied`,
  `…_unreadable`) on the existing "needs attention / retry" screen, with Korean text that says the
  setting is kept. Only a vault that was never chosen shows the first-time screen.
- Startup reconnects the vault right after local data opens, before Codex starts.
- One folder that cannot be read, or a note that vanishes between listing and checking, no longer
  fails the whole vault walk (and with it the reconnect). The vault folder itself must still open.
