## Mail accounts are read one at a time

User report on installed 0.58.96, with a screenshot of a briefing summarized at 22:03-22:04: the same
message delivered to both accounts was summarized as "body could not be read" on both copies, the
Gmail copy's Apple Mail button was disabled, and the Yonsei copy's button was enabled.

With the user's permission, a second read-only Mail diagnostic (timings, lengths and booleans only)
timed each reader step on the newest five messages of each account's Inbox and All Mail while the
Mac was idle. Every body and Message-ID was readable. Gmail cost about 0.5-1.2s per message for the
metadata properties alone; Yonsei about 20-70ms. The previous diagnostic had also seen Gmail bodies
stall for about 61s.

`collect` started one native reader per selected account concurrently, each with its own 60s
deadline. Mail answers Apple Events one at a time, so the fast account's events waited behind the
slow account's: both deadlines ran out while queued. That matches the screenshot — the Yonsei
reader finished its short link pass but not its bodies, and the Gmail reader reached neither.

Change: selected accounts are read sequentially, each keeping its own 60s deadline, so one slow
account can no longer consume another account's time. Partial-result handling, the global result
limit, attribution and fail-closed scope checks are unchanged; revocation aborts the active reader
and no further account is started. Existing summaries keep their stored text and missing links;
"다시 요약" on an item or a new briefing reads the mail again.

Not verified directly: the contention itself was inferred from the timings, the concurrency in code
and the screenshot, not measured with two concurrent diagnostic readers.
