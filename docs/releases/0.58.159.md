## The same email was summarized again, and again

Reported: "이메일이 완전히 동일한 게 여러번 요약된 것이 있음." With the constraint that matters more
than the fix: "안읽은 이메일을 missing 하는 경우는 최악이니까 그건 안전하게 double check 하고."

GOSU does keep a skip list of mail it has already summarized, so this was not a missing feature. The
key was the problem. `mailSummaryKey` names a mail by

```
sha256( sha256([accountId, mailboxPath, mailboxMessageNumber]) , receivedAt , subject )
```

Two of those three parts move. The **mailbox path** differs when the same message also sits in a
second selected mailbox, and Mail's **per-mailbox message number** changes when a message is moved
or the mailbox is re-indexed. Either one produces a different key, the skip list does not recognise
the mail, and it is summarized again — identically, which is exactly what the user saw.

A second key now sits beside the first, built on the **Message-ID**, which does not move with the
message. It is applied after the metadata read and before bodies are read, so a recognised mail
costs no body read and no summary.

### What it takes to skip, which is deliberately more than it takes to read

A mail is skipped only when **all three** agree — the Message-ID, the received time and the
subject — and only against a history item that already satisfies every existing condition: a
non-empty summary, not awaiting a body re-read, and not one of the priority-only placeholders.
Every place that _un_-excludes a mail now drops all three names together, because they live in one
map rather than two.

A mail with no usable Message-ID gets **no key at all** and is simply read. Nothing is guessed. Two
different messages cannot collide, because they would have to share a Message-ID, a timestamp and a
subject, which means they are the same message.

## Still open, deliberately

The **same-run** duplicate is not fixed here. `deduplicateVerifiedMail` merges copies only across
different accounts, so one message found in two mailboxes of one account stays two rows, and a test
pins that (`deduplicateVerifiedMail([mail('a'), mail('a')])` is expected to keep both). Changing it
means changing a deliberate invariant — the merged representation assumes one copy per account — and
that deserves its own change rather than a tack-on to this one.
