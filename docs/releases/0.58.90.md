## Briefing save cost

The first 0.58.90 full check failed: `briefing-workspace-store.test.ts` "pages beyond 600 records"
(603 sequential saves, from pre-existing uncommitted work) took 5.04–5.08s alone against a 5s limit,
and exceeded a raised 20s limit under full-check load. Profiling at 600 records (134KB file) showed a
fixed per-save cost, not growth with history: about 3ms CPU (decrypt, JSON parse, schema, serialize)
plus about 7.6ms filesystem work per save. The earlier O(n²) explanation was wrong.

Change in `SealedStateStore` (used by the Briefing workspace and generation stores): after a commit,
the instance keeps its authenticated plaintext bound to the written file identity (inode, size,
mtime, ctime). A matching `lstat` skips re-reading and decrypting; the plaintext is still parsed and
schema-validated so callers get a fresh object. Any other writer or tampering changes the identity
and forces a full authenticated read. `mkdir` runs only when the directory is missing, the envelope
is serialized once with its tag, and the temporary file is unlinked only when rename did not happen.
Atomic write, AES-GCM authentication, symlink/nlink/size checks and 0600 mode are unchanged.
Quiet-machine profile: 600 saves 12.0s → 6.0s. The 603-save test keeps a 20s limit.

New `sealed-state-store.test.ts` covers another instance's writes, a failed mutation not corrupting
the next read, tampered ciphertext rejected after its own write even with mtime restored, no
temporary files after commits or a rejected oversized write, and a commit vetoed after the
temporary file was written. These guard the safety of the optimization; they also pass on the
previous implementation because it did not cache.
