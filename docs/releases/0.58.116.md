## AI assistant tools lost the requesting client

User report: asked to add a Monday 16:00 meeting, the GOSU AI chat answered that it could not read
Calendar because "앱에 승인된 설정이 바뀌어서(assistant_settings_changed)" and told the user to save the
calendar settings again.

Evidence (tool names and error codes only, from the Claude Code transcripts of the chat runs): every
`read_calendar` call through Claude Code so far, 4 of 4 on 2026-09-19, returned
`{"error":"assistant_settings_changed","category":"permission"}` in the same second it was called,
before any Calendar read. Nothing in the settings had changed.

Root cause: `executeTool` in `briefing-assistant.ts` starts with `stillAllowed()`, which requires
`workspace.owns(profile)`; `owns` reads the requesting GOSU client from the `briefingClientContext`
AsyncLocalStorage. Provider tool calls do not run in the chat request's async context: Claude Code
delivers them from its MCP bridge (the adapter already restores only the application-language context
for this reason, see `bindApplicationLanguageCallback`). The client was therefore missing, `owns`
was false, and every tool call was reported as a changed approved scope.

Fix: `runRoutineAgent` captures the client token when a run starts and runs the provider's tool
handler inside that client context. A run started without a client still has none, so no ownership
is gained. This applies to every assistant tool and both providers, not only `read_calendar`.
