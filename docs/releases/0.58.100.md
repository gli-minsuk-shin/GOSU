## Apple Mail reading without per-position lookups

User report: reading Apple Mail is far too slow; analyze and optimize.

Read-only measurements on the user's Mac (timings, lengths and counts only; no subjects, senders,
bodies or IDs recorded). Mailbox sizes: Gmail All Mail 117,158 and INBOX 108,006 messages; Yonsei
전체보관함 3,200 and INBOX 2,790.

| Operation (Gmail All Mail, 30 messages)                      | Time          |
| ------------------------------------------------------------ | ------------- |
| `box.messages[n]` then `id()` only                           | 66.2s         |
| `box.messages[n]` then two properties                        | 60.7s         |
| AppleScript ranges (`… of messages 1 thru 30`), one property | 9–22s         |
| `messages.byId(id)` then six properties                      | 0.065s        |
| one `whose({dateReceived > …})` query                        | 14–56s, fixed |

Every Apple Event on a position-based specifier makes Mail resolve that position in the whole
mailbox (about 1–2s each in the 117k-message Gmail All Mail, 20–70ms in Yonsei), and the reader used
positions in every pass: metadata (several properties per message), Message-ID, body and source
proof. References returned by a `whose` query are id-based and cost about 1ms per property.

Per-pass profile after the change (Gmail, 25 of 101 messages from two days): links 0.018s, bodies
81s of which one message took 61s (Mail downloading the body from the server; the same message is
fast once cached), size/attachment/source/proof 0.1s. On Yonsei, raw source of large HTML mail took
1.8–12s (up to 4.3MB) although the source proof only accepts 262KB.

Changes:

- Ordinary collection asks Mail once for messages received after the coverage floor
  (`whose dateReceived > floor`), reads their received times on the returned id-based references,
  sorts them newest first and processes them. Links, bodies and proofs reuse those references. No
  pass indexes the mailbox by position. Coverage is reached when every returned reference was
  examined; the scan cap is 2,000 messages (was 250 positions).
- The source proof checks `messageSize()` (≤262,144 bytes) before `source()` is read.

Real reader, 25 messages with previews, same Mac: Yonsei 66s → 27s (partly warm bodies); Gmail
99s → 104s in that run, now dominated by the fixed `whose` scan (30s) and body downloads rather than
position lookups. The previous per-position reader would need about 1–2s per Apple Event for the
same 25 Gmail messages across metadata, link, body and proof passes.

Remaining limits: Mail's `whose` scan over a 117k-message Gmail mailbox (14–56s) and first-time body
downloads (up to about 61s per message) are inside Mail. Reading Mail's local index directly would
avoid both but needs Full Disk Access and an undocumented format; not done.

Diagnostic incident: a temporary failure-only logger on `~/.local/bin/claude` ran the CLI as a
background job, which gives it no stdin; GOSU briefing summaries started at 18:43 KST failed with
"Input must be provided either through stdin" until the link was restored. No data was changed; the
next briefing retries those summaries.
