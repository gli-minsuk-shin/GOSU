## Email and paper summaries kept breaking: one sign-in code mail stopped the whole briefing

User report: email summaries work, then after an update and a restart they stop again, over and over;
whatever is updated or restarted, email and paper summaries must work. Is Apple Mail unreachable?

Apple Mail was read fine. Evidence from the usage ledger and the Briefing AI transcripts (fields and
counts only): in the two most recent runs (2026-09-20 20:13 and 2026-09-21 08:36) the sibling batches
died 0.3 seconds after the first batch finished its save, and of all 137 email batches ever sent to the
model, exactly the three with a mail matching the "verification code / one-time / OTP / password
reset" rule were in those two runs. Two were real "one-time" passcode mails (the same two in both
runs), one was an ordinary 4,000-character mail with "one time" somewhere in its body.

The chain: `saveBriefing` refused the **whole batch** when any mail in it matched that rule and
returned null; the run read a null record id as `briefing_memory_unavailable`, a stop-the-run error
thrown outside the per-batch handling; `runBatchesConcurrently` then aborted every other batch in
flight; papers only start after emails, so they never ran; and because the run ended before mail
coverage was committed, the same mails were selected again at every later run. The briefing stayed
broken until that mail aged out of the read window, which is why it looked tied to updates and
restarts but was not.

- The rule is decided per mail (`briefing-credential-mail.ts`), tightened so "one time" alone no longer
  matches (it needs "one-time passcode/password/code/pin/link", a verification or security code, OTP,
  a password reset, or the Korean equivalents), and looks at the subject and the first 600 characters.
- Such a mail is left out of the automatic summary plan, so it is never sent to a model, is not in the
  quick briefing either (its preview can hold the code), and counts as handled. The run says so once
  ("인증 코드·일회용 비밀번호·비밀번호 재설정 메일 N통은 AI로 보내지 않고…"), for mail that arrived since today's
  previous run.
- `saveBriefing` withholds only the affected items and keeps the others; the batch narrative is dropped
  when anything in the batch was withheld. The memory store uses the same helper.
- A batch with nothing storable is finished with a notice and the run continues; only a store that
  actually failed (`historySaveFailed`) still stops the run.
- Found on the way: the run's own guard still required `intervalHours`, so a routine scheduled by its
  delivery times alone (0.58.127) was stopped at every automatic run. It now uses
  `generationScheduled`.
- Also: restoring the Apple Mail grant for the same approved scope no longer revokes it. The AI
  assistant's or Project Chat's mail search (0.58.126) could abort a running briefing's mail read.

## The models set in Settings → Agent did not reach existing chats

User report: the LLM model set in AI agent settings is not applied; it stays as it was set before.

`model-routing.v1.json` did hold the new choice (Luna low for the fast and lightweight roles, Astra
for the strong role, saved 11:02). The cause was in Project Chat: opening a chat with no stored model
wrote the role model of that day into that chat's own record
(`if (loaded.status === 'missing' && modelRouting.ready) save…`). The record was then
indistinguishable from a model picked in the chat's menu, and "presence pins the chat" kept every
chat ever opened on the old model; only chats created after the change followed Settings.

- A model picked in a chat's own menu is saved with `origin: 'user'` and stays pinned. A record
  without it (what earlier versions wrote) loads as `inherited`: the chat follows Settings → Agent
  now and whenever it changes. Nothing is saved for a chat that only follows the default.
- Consequence to know: a chat where a model had been picked by hand before this version cannot be told
  apart from an inherited one, so it follows Settings too until a model is picked in it again.
- Not changed: Briefing keeps refusing a role model from another provider than the one approved for
  the routine (`model_routing_provider_permission_required`, shown in Korean) because role routing
  is not permission to send private mail to another provider; Lecture Studio keeps the model confirmed
  when a studio is created.

## Shortcuts for Calendar, To-do and Briefing Lab

Only the AI assistant had a shortcut. Calendar, To-do and Briefing Lab now have one each, handled the
same way (intercepted in the focused GOSU window before the page, and listed in the View menu):
⇧⌘C, ⇧⌘T and ⇧⌘B by default, left-hand chords on each screen's initial. Settings → 단축키 lists
them with a modifier and key picker, a switch to turn one off, save and restore-defaults. Two screens
can never share a chord and none can take the assistant's (checked in the settings screen and again
in main, `shortcut_in_use`). Stored in `app-shortcuts.v1.json`; a damaged file is reported, not reset.

## The "AI working" star is easy to see

The running state was an 11px thin dashed outline in the dark brand green. It is now a 14px filled
star in a bright green that swells, turns and glows about once a second with two small sparks flashing
in turn beside it (the twinkling-star idea is kept). Light and dark themes have their own colours,
reduced-motion keeps the lit sparks without movement, and the finished (yellow) state is unchanged.

## A same-day briefing continues the earlier one

User request: on the same day the automatic briefing should build on the AI Assistant Summary that is
already there and add to it; it looked rewritten from scratch every time.

It was: same-day runs share one daily record, each run sees only the mail that arrived since, and the
quick first briefing ("먼저 확인할 내용") was drafted from that new mail alone and then replaced the saved
one, so the morning's points vanished at every run.

- A later run reads the briefing already saved in today's record and sends it as `previousBriefing`
  (local time, headline, points) with update instructions: say what changed since then, list what is
  new, and carry over the earlier points that still matter, dropping one only when new metadata
  resolves or replaces it. The update has its own output contract (`newPoints`, `carriedPoints`).
- `mergeQuickBriefingUpdate` puts new lines first, then the carried ones, within eight lines, removes
  repeats, and keeps the earlier lines itself when the model carries nothing over.
- The saved briefing records `previousAt` and `newPoints`; the view says which briefing it continues,
  marks new lines "새로", dims carried lines and counts the day's mail. The first briefing of a day and
  a run with no new mail behave as before (the latter leaves the saved briefing untouched).
