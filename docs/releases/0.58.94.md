## A lost Claude login is reported instead of silently failing

User report on installed 0.58.93: Briefing email summaries stopped working and the app said nothing
useful. Investigation of the plaintext usage ledger showed every Claude invocation since
2026-09-16T03:22 (KST) failing in under a second; the local CLI reported
`loggedIn: false, authMethod: none` and a probe returned
`Failed to authenticate: OAuth session expired and could not be refreshed`. The stored login was
lost when the CLI was updated to 2.1.272 earlier that night.

GOSU misread that state twice. `claudeAuthRequired` matched only the older wording ("OAuth access
token has expired", "re-authenticate to continue"), so the new sentence fell through to a generic
result failure. And a refresh that failed authentication left the previous catalog in place, so the
app kept looking connected after the login was gone.

Change: the expired-login test matches the wording family (expired OAuth token or session, "could
not be refreshed", "failed to authenticate", "run /login") and still requires the CLI's own error
envelope. A catalog refresh that finds no stored login (`loggedIn` other than true) now drops the
cached connection, and later work reports `claude_code_auth_required` rather than
`claude_code_not_connected`, so Briefing shows its existing "log in to the subscription again"
guidance. A different authentication method (an API key) keeps reporting
`claude_code_subscription_required` and is not treated as an expired login.

## Briefing names the failure instead of blaming the network

Provider turn failures that Briefing had no message for fell through to "check the network or the
response format", which is wrong and unactionable for an AI execution failure. Change: Briefing
reports a lost provider connection and a failed provider turn in their own words, and any remaining
unmapped internal code is shown as `(오류 코드: <code>)`. Only our own snake_case identifiers are
printed; provider text still never reaches the message.

## The model that runs a summary is named

User request: show which model Briefing uses. A summary follows the role assigned in Settings, which
can differ from the model picked in the Briefing chat, and the existing model line only appears
after a summary succeeds. Change: the connecting progress detail now names the provider, model and
reasoning that are about to run.

## Apple Reminders can be authorized at all

User report: adding a Briefing task never reached Apple Reminders. The macOS privacy database has no
Reminders record for GOSU, while Calendar and Mail automation are both granted to
`science.gosu.desktop` — macOS attributes the bundled bridge's request to the host app, and the host
declared Calendar and Apple Events reasons but no Reminders reason, so the prompt could never
appear. Change: the packaged host declares `NSRemindersFullAccessUsageDescription` and
`NSRemindersUsageDescription`. The user still grants access once in Briefing settings.
