## Remaining Codex and Claude plan limits in the title bar and on the Usage screen

User request: show the remaining weekly usage of Codex and Claude in the GOSU title bar, only for
connected services, and let the Usage screen show the details "roughly like Codex": how often the
numbers refresh (30 min, 10 min, 1 min, 30 s, 10 s …), what is actually left, the weekly and the
5-hour window, and when each one resets. After seeing the first preview the user asked for the title
bar text to be smaller and not bold ("지금은 너무 눈에 띔").

- **Where the numbers come from.** GOSU asks each CLI for its own numbers with the CLI's own login; it
  reads no credential and sends no model request, so refreshing spends nothing.
  - Codex: `account/rateLimits/read` on the app-server connection GOSU already holds (new
    `CodexAppServer.rateLimits()`), plus the `account/rateLimits/updated` notification Codex pushes
    after its own turns. Observed 2026-09-21 (CLI 0.153.4, Pro): only `primary` was reported and it
    was the weekly window (10,080 minutes), `secondary` was null. Windows are therefore named by
    their length, not their slot: up to a day is the short "session" window, six to eight days is
    "weekly".
  - Claude Code: the CLI's control request `get_usage` (the data behind its `/usage` screen), sent to
    `claude -p --input-format stream-json …` with no prompt. Observed 2026-09-21 (CLI 2.1.272, Max):
    `five_hour` and `seven_day` with `utilization` in percent and an ISO `resets_at`, the per-model
    weekly limits in `model_scoped` ("Fable"), `extra_usage`, and a session cost of 0. One read takes
    about 0.8 s including the process start, 0.5 s on a process kept alive; the CLI holds about 220 MB
    while it runs. The probe starts in safe mode (no user hooks, plugins or MCP servers), without
    session persistence, with the API-key variables removed from its environment. An older CLI
    answers "Unsupported control request" and is reported as `usage_limits_unsupported`. The SDK names
    this call experimental, so the answer is parsed defensively and an unknown shape is reported as
    `usage_limits_format` instead of showing nothing. (The `rate_limit_event` of a normal request
    carries the same two windows, but needs a model request: 3,710 input tokens on Haiku per read.)
- **Refresh** (`UsageLimitService`, settings in `<userData>/usage-limits.v1.json`, mode 0600): every
  10 s, 30 s, 1, 5, 10 (default) or 30 minutes, only while the GOSU window is visible and not
  minimized; showing the window again refreshes at once, as does a service that connects or
  disconnects and "지금 새로고침". One read at a time. Below one minute the Claude CLI is kept running
  between reads; otherwise it is started per read and exits. A failed read keeps the last good numbers,
  records a stable code (`usage_limits_unavailable`, `_auth`, `_timeout`, `_unsupported`, `_format`,
  `_failed`) and waits longer before the next scheduled attempt (doubling, at most 10 minutes).
- **Connected services only**: Claude Code is asked only while it is connected in GOSU; a CLI that is
  not logged in (or cannot be started before any successful read) counts as not connected. Such a
  service is absent from the title bar and explained on the Usage screen.
- **Title bar** (`UsageLimitPills`): per connected service what is left of the weekly window, or of the
  only window its plan reports: "Codex 주간 87%", "Claude 주간 68%". Caption size, regular weight,
  muted, no border; only a limit with 10% or less left turns its number red, and numbers from a failed
  refresh get a dashed outline. The tooltip lists every window with used, left, reset time and
  countdown. A click opens the Usage screen. It can be turned off there.
- **Usage screen** (`UsageLimitsPanel`, first section): per service the plan, every window (5-hour,
  weekly, weekly per model) with a meter, "N% 남음", "N% 사용", the reset time and a countdown, whether
  extra usage or credits are on, the time of the last read, the reason of a failed refresh next to the
  last known numbers, the refresh interval, the title bar switch and "지금 새로고침".
- **Failures are shown**: a provider's failed read keeps its numbers with the code and a sentence; a
  failed "지금 새로고침" or settings change shows its reason in the panel (the hook drops no error);
  a settings file that cannot be read is reported in every status
  (`usage_limit_settings_unreadable`), the defaults run, and saving a setting writes it again.
- IPC `gosu:usage-limits:status`, `:refresh`, `:configure` (settings validated by schema; nothing
  takes a provider, a path or a command) and the pushed `:changed`, validated in preload.

Seen in a browser (the real components rendered to a static page with the real answers of both CLIs,
768px viewport the user had chosen, light and dark): the title bar display before and after the
restyle, the panel with normal numbers and with low, critical and stale ones. Found and fixed there:
the second pill was clipped by the sync pill at narrow widths (the subtitle gives way now), the
settings row wrapped under an oversized checkbox, the read time used the English clock format, and the
percentage inherited the GOSU wordmark style from `.titlebar strong`. Checked against the real Claude
CLI through the repository's test runner: two reads, windows parsed, session cost 0, no process left.

## Project archive: easier to find

User request: "project 를 아카이브로 옮기는 기능을 넣자. Project 가 너무 많으면, 보기에 난잡함." The feature
existed (sidebar ••• menu → "보관", a "보관됨" group with "복원", Settings → Projects), but under a word
the user did not connect with archiving and behind a small menu button.

- Right-click on a project in the sidebar opens the same actions menu; the row's tooltip says so.
- Korean wording is "아카이브" throughout: the menu item "아카이브로 이동", the group "아카이브",
  Settings → Projects "아카이브한 프로젝트", and the same in the shell, help and error catalogs (the
  shell catalog also defines `Archive`/`Archived` and takes precedence over the desktop one, which
  the new language test caught). "보관" stays where it means keeping data or the paper library.
- The confirmation after archiving was an untranslated English string. It now reads
  "{name}을(를) 아카이브로 옮겼습니다. 프로젝트 목록 아래의 ‘아카이브’에서 복원할 수 있습니다."; the restore
  confirmation and the "restore before opening this search result" notice are translated too.
- Not changed: what archiving does (it hides the project from the list, Tasks, notifications and the
  assistant, and blocks edits until restored), archived projects in search results and in the Usage
  project filter.

## Briefing Lab: ⇧⌘Enter runs a new briefing

User request. ⇧⌘Enter (⇧Ctrl+Enter elsewhere) anywhere in Briefing Lab does what the "브리핑 생성"
button does, under the same conditions (settings loaded, no request pending, no run in progress); it
is ignored while an input method is composing and on key repeat. The button's tooltip shows the chord.
When the desktop window (sidebar, title bar) has the focus instead of the Briefing frame, the shell
forwards the chord to the frame (`gosu-briefing-run-now`, accepted from the parent window only);
Calendar and the assistant, which share the frame, do not get it.

## Briefing: the reason behind a run's warning opens again

User report on 0.58.135: after a new briefing an error mark appeared, and clicking it showed no
detail ("error 가 떠도 그게 뭔지 자세한 error message 를 클릭해도 안보여줌"). The collapsed warning
beside the page title is a `<details>`; its text was a `<p>`, and the compact header hides every `<p>`
(`workspace.css`: `.briefing-main-header p { display: none }`). The progress line had an override for
this, the warning never did, so opening it changed only the chevron. Measured with the real CSS: the
`<p>` had `display: none` and no height, the replacement is a 420×76px panel with three lines.

- The text is now `<div class="briefing-generation-alert-detail">`, styled in both places the alert
  renders (beside the title as a panel, under the controls inline).
- A run's warnings are stored one per line instead of joined by spaces and shown that way
  (`white-space: pre-wrap`), still capped at the stored 1,000 characters.
- What the user's run had recorded was not read (sealed store). The local usage ledger shows the 12
  summary calls since the 0.58.135 install all succeeded on Codex `gpt-5.6-luna`, the model Settings →
  Agent assigns, so the mark was a warning of a completed run, not failed summaries.

Regression tests: `usage-limit-contracts.test.ts` (new, 4: both real answers, window naming by
