## Scheduled briefings failed every time

User question: why is 자동 브리핑 paused?

The pause ("자동 브리핑 일시 중지 · 설정 확인 필요") is set by the scheduler before a run when the saved
approval no longer matches the settings (AI provider, mail accounts or mailboxes, mail reading or AI
use, calendars, to-do or project reading), when the request policy is "ask every time", or when the
routine's ownership cannot be confirmed; the reason is stored and shown when the notice is opened, and
the schedule stays paused until the interval is selected again. The stored reason was not read here
(the generation file is sealed with the Briefing key, and reading it could prompt the keychain). The
client token that owns the schedule is kept in local storage and survives reinstalls, so ownership was
not lost by today's updates.

While tracing this, a separate defect turned up: a scheduled run through the real service always
failed with "설정 또는 자동 실행 권한이 변경되어 생성을 중단했습니다". The scheduler stores its approval as
`generationProfileDigest` ("v2:…"), but the run's own guard in `generateDaily` compared the stored
value with `generationRunDigest`, a different digest, so the two never matched. Existing scheduler
tests replaced the run with a mock and did not reach that guard.

- The guard now checks the schedule with `generationProfileMatches` (the scheduler's own check) against
  the current profile, together with the interval and the always-allow policy.
- Resuming still takes one step from the user: select the interval again.
