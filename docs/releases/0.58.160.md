## 논문 요약 holds one conversation for the page, not one per paper

"논문 하나당 논문 요약 AI chat 을 만들지 말고 논문 요약 page 안에 있는 모든 논문들을 하나의 AI chat 에
넣자. 이렇게 하면 나중에 대화 나눈걸 찾기도 어렵고 너무 번거로움."

A paper is now something a **turn** carries, not something that forks the transcript. Pressing
「AI 질의응답」 attaches that paper to the next question and opens the page's conversation; it never
starts a second one. The attachment shows as a chip over the composer and can be taken off with the
conversation left open, because detaching is not closing.

Two things had to be got right, and both were found by reading the store rather than by trying it.

**"One conversation" could not mean dropping the paper key.** `conversationScope(profile, paperKey?)`
returned the bare profile scope when there was no key — and that scope is the AI 비서's own thread.
Implemented the obvious way, 논문 요약 would have merged straight back into the assistant, undoing
0.58.152 through 0.58.155 in a single line. The page conversation carries its own fixed mark, which
keeps the `:paper:` prefix so every rule that separates the two chats works unchanged.

**A bare optional string could not say which chat a turn belonged to.** With one conversation, a
follow-up can be asked with nothing attached — and a turn with no paper key was the assistant's by
definition, so that follow-up would have landed in the AI 비서's transcript. The parameter is now
`chat?: PaperChatSelector`: `undefined` is the assistant, `{}` is 논문 요약 with nothing attached,
`{ paperKey }` names the paper that turn is about. Changing the type made the compiler list all
twenty call sites, and the request now **states** which chat it is instead of inferring it from
whether a paper happens to be attached.

Attribution moved from the scope to the turn, so the card's AI mark, the 「AI 질의응답」 filter and
`paperConversationIndex` — which AI 비서, Project Chat and Model Lab read — keep working off the new
record. Conversations already written one thread per paper are read, never merged and never
rewritten: a pure function, `paperTurns`, reads both shapes and is mutation-checked against dropping
the legacy branch.

## The same email in two mailboxes of one account is one row

This section is another session's work, recorded here because it shipped in this package; the
findings below are its measurements.

`deduplicateVerifiedMail` merged copies only across different accounts, so a message sitting in both
the inbox and an archive of a single account had nowhere to be recognised and showed twice.
`sameMessageTwice` collapses it on stricter evidence than the cross-account rule: the Message-ID,
the subject **and** the received time must all agree. The time is deliberate — a sender that reuses
a Message-ID across two real sends differs in time, so requiring it keeps the "never hide an unread
mail" property the rest of the mail work is built on. No Message-ID, no match. The twin is dropped
rather than folded into `mailCopies`, and whichever copy has a body is the one kept.

Two findings changed that change, both measured rather than argued:

An existing test pinned `deduplicateVerifiedMail([copy('a'), copy('a')])` at length 2. The session
had predicted it would not be in the way because the `mail()` fixture carries no Message-ID — true,
but the `copy()` helper adds one, so it broke. The expectation was changed rather than routed
around, and the original intent kept as its own explicit assertion: `sameDeliveredMail` still
refuses a same-account pair, so `mailCopies` still means one copy per account. Only what happens
afterwards changed.

Dropping the twin would have pinned that mailbox's coverage forever. `nextMailCoverage` treats any
read row that is neither summarized nor named by a `copyIds` entry as unhandled, sets
`reached = false` and raises the lower bound to it — so GOSU would have re-read from that message on
every run, having been asked to read less. Putting the twin in `mailCopies` fixes the bookkeeping
and breaks the screen instead: `briefing-insight-card.tsx:291` counts that array for
"같은 메일 · n개 계정 수신" and would claim two accounts where there is one. A separate stand-in
path, `mailRowRepresentatives`, serves the coverage bookkeeping without touching what the card
counts.

This closes the same-run half that 0.58.159 recorded as deliberately deferred.
