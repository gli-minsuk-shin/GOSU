## 논문 요약 AI really is separate from AI 비서 now

Reported for the third time: "논문 요약 AI 를 별도로 해달라고... AI 비서랑 섞지 말고." The user was
right, and 0.58.152's separation was only half wired.

0.58.152 stopped the paper button from **opening** the AI 비서 pane. It left the wire that **hands
the paper to it** connected: `briefing-app` passed the clicked paper to `RetainedBriefingChats`,
which passed it to the assistant's chat, which stored it as the attached paper and moved the cursor
into its composer. So every question about a paper still attached that paper to the AI 비서's next
turn — the exact mixing the separation existed to remove.

Found by rendering the app in a test and reading the tree: the assistant's composer held the paper's
name tag and its 「참조 논문 해제」 button, with the paper's own conversation open at the same time.

The wire is cut and the path behind it is gone: the prop, the effect that stored it, the state, the
composer tag and its dead CSS. The AI 비서 can no longer be handed a paper by anything. Only the
paper's own conversation carries a paper.

## Pressing a paper's own button looked dead, again

Same screen, different cause, and the reason 0.58.153's fix did not settle it. That fix covered
arriving from another tab, where the screen mounts scrolled to the top. It did not cover the ordinary
case: already in 논문 요약, pressing a paper's button.

The conversation panel is the **last element on the screen**, under every paper card, and
`.briefing-reading-list` is `overflow: hidden`, so the page is what scrolls. Opening the panel changed
state and moved nothing the user could see. With thirty cards above it the panel opens thousands of
pixels below the viewport.

The panel now scrolls itself into view when it opens, and takes focus, so the keyboard lands in the
conversation too.

## One paper, one conversation, whichever button asks

Found while fixing the above. A row offers two ways in: the card's own 「AI 질문」 and the row's
「AI 질의응답」. The row's carried the paper's link; the card's did not. A paper held by a briefing
rather than by the library is keyed by that link, so the two buttons opened **two different
conversations for one paper** — `item:briefing-run-1…` against `arxiv:2601.00001v1`, measured. Ask
through one and the questions asked through the other were nowhere to be seen.

Both buttons now build the same reference.

## Riding along: the flaky process-group test is fixed

Not my change. A separate session reworked `apps/desktop/test/manuscript-pdf-compiler.test.ts`
(test file only, 141 insertions and 65 deletions, no app source), and the user chose to let it ride
in this release rather than take a version of its own. It closes both the flake 0.58.154's record
flagged and the open item left in MAINTENANCE_GUIDE's 0.58.96 entry.

The three "manuscript PDF command process groups" tests no longer assert that a forked child's
side-effect file never appeared within 350 ms — a race the machine decided. They plant a `sleep 30`
in the command's process group, publish the group id by atomic rename **after** the fork, and poll
`process.kill(-pgid, 0)` until it throws ESRCH. A slow machine can only make the group die later,
never make the assertion wrong.

Their evidence: removing `process.kill(-pid, 'SIGKILL')` from the runner's `terminate()` now fails
all three, where before the rework it failed only two — the timeout test had never tested the
guarantee at all. Under twenty CPU busy loops on ten cores the old file failed twice in eight runs
with the exact reported assertion; the reworked file ran twelve for twelve clean. A test file is not
a build input, so `app.asar` is unaffected and the bundle needs nothing verified for it.
